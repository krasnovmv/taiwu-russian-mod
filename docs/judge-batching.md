# Дизайн: батчи в судье

Статус: **реализовано** (2026-08-23). Живой замер на `EncyclopediaAssets`:
40 юнитов → 30 контекстов → 1 запрос; 67 → 51 → 2 запроса; ошибок разбора 0.

Судья (`npm run judge`) шлёт по одному запросу на группу дубликатов. Корпус
большой, юниты в основном короткие, и на короткой строке модель почти не
рассуждает — запрос уходит на накладные расходы, а не на работу. Задача: класть
в один запрос несколько юнитов.

## Что уже есть в коде

- `judgeTm` сворачивает работу в группы по `verdictKey` (одинаковый
  EN/CN/глоссарий/движок → один запрос, вердикт веером на всех членов).
- `ChatSession` — окно диалога поверх stateless-бэкенда; писалось как слой, на
  который батчи и сядут.
- Замер из `session.ts`: на **батчах по 40** сессия давала reasoning-токены
  5870 vs 9940 (−41%) и 2.31 vs 1.64 юнита/с (+41%). На одиночных ходах —
  наоборот, на 20–25% медленнее. Отсюда `JUDGE_SESSION_TURNS = 1` по умолчанию.

## Решения

| Развилка              | Решение                                                        |
| --------------------- | -------------------------------------------------------------- |
| Границы батча         | только внутри одного файла (`judgeTm` остаётся единицей)       |
| Размер                | `TAIWU_JUDGE_BATCH=40` групп И `TAIWU_JUDGE_BATCH_CHARS=12000` |
| Порядок групп         | TM-овый, без сортировки по длине                               |
| Формат ответа         | массив записей с `id`, поюнитный ретрай                        |
| `JUDGE_VERSION`       | остаётся 9, не бампаем                                         |
| `JUDGE_SESSION_TURNS` | остаётся 1, включается флагом после замера                     |

Глобальная очередь через все файлы (чтобы сотни мелких файлов не тратили по
недобитому батчу) — сознательно **вне этой задачи**.

## 1. Единица запроса

`groupList` → `batchGroups()` → батч = список групп → `mapPool` → один запрос.
Веер вердиктов на членов группы, пороги MQM и QA-гейты не меняются.

Порядок групп — TM-овый. Соседние ключи это соседние строки одного раздела
файла: один регистр, одна тематика, модели это скорее помогает. Разброс длин
гасит символьный бюджет, сортировка не нужна.

## 2. Мемо разрешается до сборки батчей

Сейчас `memo.get` живёт внутри пула, и батч мог бы наполовину состоять из уже
решённого. Порядок становится: погасить все хиты кеша (тик прогресса,
`reused`), собрать батчи только из оставшейся работы.

Потери нет: `memoKey` тождественно равен ключу группы, значит двух групп с одним
`memoKey` внутри файла по построению не бывает, и внутрифайловых хитов, которые
раньше срабатывали бы «по ходу», не существует. `--force` по-прежнему не читает
мемо, но пишет.

## 3. Границы батча

`batchGroups(groups, maxUnits, charBudget)`: набирать группы, пока не упрётся
либо в `maxUnits`, либо в `charBudget`. Стоимость группы = длина
`en + cn + ru` её головы (в промпт идёт только голова).

- `TAIWU_JUDGE_BATCH` — 40 групп.
- `TAIWU_JUDGE_BATCH_CHARS` — 12000 символов.
- Группа тяжелее бюджета едет своим батчем и никогда не выбрасывается — та же
  дисциплина, что у `batchByChars` в `engine/yandex.ts`.
- CLI: `--batch N`. `--batch 1` = сегодняшнее поведение.

## 4. Формат обмена

Юзер-сообщение: те же блоки `FILE / KEY / ENGLISH / CHINESE / RUSSIAN /
MACHINE / GLOSSARY`, каждый под заголовком `UNIT <n>`, через разделитель.
`buildUserMessage` остаётся сборщиком **одного** блока (сигнатура и вывод не
меняются); над ним появляется `buildBatchMessage(ctxs, glossary)`.

Схема ответа:

```json
{ "units": [ { "id": 1, "errors": [ … ], "ru": "" } ] }
```

Путь кода один: батч из одного юнита тоже отвечает массивом.

Правка системного промпта минимальная — «даётся один или несколько юнитов,
ответ содержит запись на каждый UNIT id». Правила, пороги, категории и гейты не
трогаются.

### Почему `JUDGE_VERSION` не двигается

Прецедент уже установлен сменой бэкенда и `session-turns`: они меняют, **как**
модель спрашивают, а не **что** у неё спрашивают, и вердикты не
инвалидируют. Батчинг из того же ряда — форма обмена. Правила, severity-порог и
QA-гейты идентичны. Практическое следствие: ~1300 уже отсуженных файлов
остаются в силе, `cache/judge.jsonl` продолжает играть.

## 5. Порча ответа

Три случая, три разных исхода:

1. **Юнита нет в ответе, или `id` чужой/дублирующийся.** Только этот юнит
   остаётся неотмеченным и немемоизированным (уходит в ретрай следующего
   прогона). Соседи по батчу применяются нормально. Считается в `errors`.
2. **Ответ не парсится целиком.** Батч делится пополам и переспрашивается,
   рекурсивно до одного юнита. Без деления теряются все 40, а следующий прогон
   соберёт ровно тот же батч тем же алгоритмом и упадёт так же — вечная петля.
   С делением плохой юнит изолируется за ~2·log₂(N) лишних запросов в худшем
   случае, остальные доезжают.
3. **QA завернуло правку.** Как сейчас: поюнитно, `session.rollback()`, ничего
   не отмечается и не мемоизируется.

Отдельный риск батчинга — обрезание ответа по лимиту генерации: 40 записей с
`explanation` до 240 символов это заметный выход. Смягчается делением из п.2 и
`TAIWU_JUDGE_EXPLANATIONS=0`.

## 6. Побочные правки

- **Окно сессии.** `MAX_HISTORY_CHARS = 20_000` в `session.ts` при батчах по
  12000 схлопнет окно до двух ходов и обессмыслит `--session-turns`.
  `ChatSession` получает `maxChars` параметром (дефолт прежний — существующие
  тесты не двигаются), `judgeTm` передаёт `max(20_000, 3 × batchChars)`.
- **Чекпоинт.** `JUDGE_CHECKPOINT` считает группы, а батч теперь крупнее
  чекпоинта. Чанк становится `max(concurrency, ceil(CHECKPOINT / batch))`
  батчей — иначе `mapPool` получает один элемент и параллелизм умирает.
- **Статистика.** В `JudgeStats` добавляется `requests`, CLI его печатает —
  иначе выигрыш от батчей не виден. `judged` переопределяется как «получено
  вердиктов по группам» (было «запросов»).

## 7. Тесты

- батч шлёт один запрос на N групп и веерит вердикты на всех членов;
- символьный бюджет режет батч, перетяжёлая группа едет одна;
- пропущенный `id` оставляет свой юнит ретраибельным, а соседей применяет;
- нераспарсенный батч делится и спасает исправную половину;
- QA-реджект внутри батча роняет только свой юнит;
- `--batch 1` даёт то же, что и до батчинга;
- мемо-хит гасится без запроса и не попадает в батч.
